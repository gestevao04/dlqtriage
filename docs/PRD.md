# PRD — DLQ Triage Agent

## Vision and goal
Cut the manual work of handling Dead Letter Queues: an agent classifies each
failure, investigates the cause with read-only tools, and recommends (and,
only under explicit policy, performs) the next action. Everything else
reaches a human with a ready-made diagnosis. It is also a public reference
project for agentic engineering: evals, guardrails, observability and MCP.

## Personas
- **On-call developer:** gets DLQ alerts and needs a fast diagnosis.
- **Tech lead / service owner:** sets policy (what may be reprocessed
  without a human) and audits decisions.

## Problem and value proposition
Investigating a DLQ is repetitive: read the stack trace, check the schema
and domain state, decide between reprocess, discard or escalate. The
proposal is a structured, auditable triage with autonomy limited by an
explicit policy.

## MVP scope
- DLQ consumption (Kafka) with idempotency and persistence (PostgreSQL).
- Deterministic baseline classifier + eval dataset and harness.
- Investigator agent (LLM + read-only tools) with structured decisions.
- Guardrails (confidence, risk, step/cost limits, autonomy switch), a
  human approval queue, and reprocessing executed after approval.
- Observability: traces, metrics and a per-run audit trail.
- MCP server for querying failures and diagnoses and approving actions.
- Sandbox failure generator for demos and evals.

## Out of scope
SQS adapter (post-MVP), web UI, multi-tenancy, user authentication beyond a
static token, automatic discard, automatic payload repair, model
fine-tuning, cloud deployment. Automatic reprocessing (`AUTO` mode) is
implemented behind the policy but disabled by default.

## Success metrics (measured by the eval harness)
| Metric | MVP target |
|---|---|
| Classification accuracy (100+ case dataset, held-out split) | >= 85% (agent); baseline reported |
| Dangerous actions (recommended reprocess where escalation was correct) | 0 |
| Unnecessary escalations | <= 20% |
| Invalid LLM outputs handled without acting | 100% |
| Cost per message (local profile) | US$ 0 |
| Average steps per investigation | <= 4 |
| Decisions with a complete audit trail | 100% |

## Risks and assumptions
- Risk: synthetic dataset may not represent real failures. Mitigation:
  variations generated by several different LLMs, human review sampling,
  held-out split, provenance recorded per case.
- Risk: prompt injection via payload.
- ASSUMPTION: local Ollama models support reliable tool calling. The eval
  harness will confirm or refute this.
- ASSUMPTION: local Kafka is enough; no high-availability requirement.
